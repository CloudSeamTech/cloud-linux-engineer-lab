Reality check — read this first

You cannot legally or technically stand up a real IL6 system at home. True IL6 (classified up to SECRET) runs only in Azure Government Secret: a SIPRNet (Secret Internet Protocol Router Network)-connected, ICD (Intelligence Community Directive) 705-accredited, cleared-US-citizen-operated dedicated cloud. This lab uses ordinary commercial Azure to teach the transferable engineering and the control framework (RMF (Risk Management Framework) · NIST (National Institute of Standards and Technology) 800-53 · DISA STIGs (Security Technical Implementation Guides) · DoD (Department of Defense) SRG IL5 (Impact Level 5) baseline + ~94-control classified overlay). Master this and you walk into the accredited environment already fluent.

Keep it cheap — the prime directive

Cost is driven by running VMs (Virtual Machines) and disks. Set a budget + alert in Phase 0, use B-series burstable VMs, enable auto-shutdown, and deallocate (stop) every VM when you log off. Fully deallocated, this lab costs near $0/month; left running carelessly it can hit $100+. Intune needs a license — use a free EMS E5 / M365 trial. Treat "terraform destroy at end of session" as a habit, not an afterthought.

Cost control — staying under $100/month

Glance at this before every session. The lab is build → prove → screenshot → tear down — not leave-it-running. The only way to overshoot $100 is forgetting to delete the firewall/AKS or leaving a VM on.

Free or pennies — build all you want
  • VNets, subnets, NSGs, route tables (UDRs), peering — free.
  • Azure Bastion Developer SKU — free; use it for single-VNet labs instead of Basic.
  • Key Vault, Storage — pennies. AKS control plane (Free tier) — $0; you only pay for the node VM.
  • Entra ID, Azure Policy, Defender CSPM — free tiers. New accounts get a $200 credit for 30 days.
Budget-killers — deploy, prove, then DESTROY the same day
  • Azure Firewall — ~$1.25/hr Standard (~$900/mo if left on), ~$0.40/hr Basic (~$335/mo), plus ~$100/mo per policy. Run it an hour for the hub-and-spoke lab, then kill it.
  • AKS worker nodes, a large always-on VM, Bastion Basic (~$140/mo), and VPN / NAT Gateway — same rule.
Cheap with discipline
  • Small B-series VM — B1s ~$8/mo, B2s ~$30/mo if left on 24/7. Deallocate (stop) it when idle and you pay only a few dollars for the disk.
End-of-session teardown checklist
  • terraform destroy — or delete the whole resource group (everything inside goes with it).
  • Deallocate any VM you are keeping; confirm Firewall, AKS, and Bastion Basic are gone.
  • Check Cost Management → Cost analysis; keep your Phase 0 budget alert at ~$50 and ~$90.

How you'll work

Visual Studio Code is your workbench — that's where the heavy lifting happens. You write the Terraform, Ansible, and scripts there, run az, terraform, git, and kubectl from its built-in terminal, and use Remote-SSH (Secure Shell) to edit straight on your Linux VMs. The Azure portal is for viewing and verifying, not building. The loop is: edit code → run it in the terminal → commit to git → apply.

Your reusable lab VM (Infrastructure as Code)

The repo ships a ready-to-run lab-vm/ folder (Terraform + cloud-init + a Makefile) that builds your exact hardened AlmaLinux VM from code. One-time: az login, install Terraform + Azure CLI, run ssh-keygen, set allow_ssh_cidr to your own IP, and accept the free image EULA: az vm image terms accept --publisher almalinux --offer almalinux-x86_64 --plan 9-gen2. Then the loop is: make up (build) → make ssh (log in) → make stop (deallocate — keeps your data, ~$0 compute) or make down (destroy; rebuild later with make up). The hardening lives in cloud-init.yaml, so every rebuild is identical — never hand-tune. The full rep loop and the deallocate-vs-destroy explainer are in lab-vm/README.md.

Runbook: zero → AlmaLinux VM → internal HTTPS site

This is the real remote-engineer setup: you run the commands from your own laptop (VS Code's terminal), while all the infrastructure lives in Azure. The lab-vm/ and nginx-tls/ folders are in your GitHub repo — clone it and cd into the folder. Stage 1 builds the machine in Azure; Stage 2 builds the site on it. (Want zero local installs instead? Run Stage 1 in Azure Cloud Shell — see the note under the commands.)

# --- Stage 1: from your laptop (VS Code terminal) --- build the VM IN Azure
az login                               # sign in to your Azure subscription
git clone <your-repo> && cd lab-vm    # the lab-vm folder is INSIDE your repo
curl ifconfig.me                       # your home IP -> set allow_ssh_cidr in terraform.tfvars
make up            # Terraform builds a fresh hardened AlmaLinux VM in Azure
make ssh           # SSH from your laptop into the Azure VM

# --- Stage 2: on the VM --- build the internal HTTPS site
sudo dnf install -y podman openssl
git clone <your-repo> && cd nginx-tls    # same repo, the nginx-tls folder
chmod +x *.sh
./make-internal-ca.sh                        # your internal CA (private PKI)
sudo cp ca/ca.crt /etc/pki/ca-trust/source/anchors/lab-ca.crt && sudo update-ca-trust
./issue-cert.sh                              # generate CSR -> CA signs -> install cert
./run-nginx.sh                               # NGINX-in-a-container serves HTTPS
echo '127.0.0.1 internal.lab' | sudo tee -a /etc/hosts
curl -v https://internal.lab:8443           # verify: trusted, TLS 1.2+

# renew anytime by re-running ./issue-cert.sh   |   tear down with: make down

Where things live: only the CLI tools (az, terraform, git, ssh) and your repo clone sit on your laptop — every VM, network, and container is in Azure. That is exactly how a remote cloud engineer works from home: laptop drives, cloud hosts. Lock allow_ssh_cidr to your home IP so only you can reach the VM. No local installs wanted? Run Stage 1 from Azure Cloud Shell (browser, with az/terraform/git preinstalled) instead — just note its IP changes per session, so reset allow_ssh_cidr each time (or use Azure Bastion).

Job-description decoder: Zero Trust, DevSecOps & FISMA — you already built these

Cleared cyber-engineer postings (Peraton, GDIT, Booz, etc.) use framework vocabulary for things this lab does hands-on. Learn the mapping so you can claim your own work in their language:

Zero Trust Architecture (ZTA) — "never trust by network location; verify every request." You implemented its pillars: identity as the perimeter (MFA + Conditional Access + PIM — 7.1, 7.6), least privilege (RBAC scopes — 0.4, 7.1), micro-segmentation (NSGs, private endpoints, no public IPs, Bastion-only admin — 2.2, 2.3, 2.6), assume breach (centralized logging, detection, automated response — 6.2, 10.3), and verified devices (Intune compliance — 5.3). Interview line: "My lab is Zero Trust end to end — no admin port faces the internet, every request is verified by identity and device, and I assume breach with Sentinel watching."

DevSecOps — security checks embedded in the pipeline instead of bolted on at the end. Your 1.7 IaC scanner running automatically inside your 7.8 gated pipeline (with OIDC, no stored secrets) is DevSecOps — the "shift left" pattern by name. Interview line: "Every commit is scanned and planned before a human approves the apply — security is a pipeline stage, not an afterthought."

FISMA High / NIST 800-53 high-impact — FISMA is the federal law requiring the RMF process you learned in 0.1; "High" is the strictest control baseline (more controls, stricter parameters) for systems whose compromise would be catastrophic — satellite ground systems, for example. Your scan-remediate-document-evidence loop (3.4, 4.2, 6.4, 8.2–8.3) is exactly that work at lab scale.

Translation table: "SOPs" = your runbooks (7.4) · "attack reconstruction / forensics" = your Sentinel investigation graph + KQL timelines (10.3) · "vulnerability remediation solutions" = your scan→prioritize→patch→verify loop (5.4, 5.6, 6.3) · "secure network connectivity monitoring" = Network Watcher + flow logs (2.5, 10.3) · "configuration guides & architecture diagrams" = your 8.4 diagram with control mapping.

Is this how real enterprises actually work?

Mostly yes — and that's the point. The core of what you do here is exactly what enterprise and government teams do every day: define infrastructure and config as code, work from an editor like VS Code with a terminal, drive everything through CLIs (az, terraform, git, kubectl), keep it all in version control, and ship changes through reviewed pipelines. Those muscles transfer directly.

What's different at enterprise / classified scale is the guardrails around that style — not the style itself:

  • Your workstation is managed. You won't freely install whatever you want — software comes from an approved catalog (pushed via Intune/MECM (Microsoft Endpoint Configuration Manager)) and admin rights are restricted. In classified work you're on government-furnished equipment inside an accredited facility, often a VDI (Virtual Desktop Infrastructure)/thin client with no internet.
  • Version control is internal, not public GitHub — GitHub Enterprise, GitLab, Azure DevOps, or an air-gapped internal server.
  • No open internet for packages — tools and updates come from internal mirrors (Artifactory/Nexus, internal repos), not the public registries.
  • You don't hold standing admin. Privileged access is just-in-time (PIM (Privileged Identity Management)), often from a dedicated privileged-access workstation, and credentials come from a vault (Delinea) — you rarely type a password.
  • You usually don't deploy to production from your laptop. A pipeline runs terraform apply with an approver and separation of duties; your job is the code and the pull request.
  • The cloud is GovCloud / Azure Government (and at IL6, the classified Secret cloud) — same tools, different endpoints and controls.

Nothing you learn here is wasted — it's the same workflow with more controls layered on. Building it the open way first is how you get fluent enough to thrive once those controls are in place.

How to work through this — in order

These phases are built to be done top to bottom, and each one assumes the last is finished. Starting from a brand-new Azure account: do the Prerequisites tab first, then walk the phases in this order — it respects what depends on what.

  • Prerequisites → install your tools + set a budget alert (free)
  • Phase 0 · Foundations → learn the landscape and cost guardrails; no resources yet (free)
  • Phase 1 · Infrastructure as Code → learn Terraform; build & destroy a resource group (≈ $0)
  • Phase 2 · Networking → the private network spine
  • Phase 3 · Active Directory → the identity backbone (everything starts with identity)
  • Phase 4 · Linux → your first server (the web tier)
  • Phase 5 · Patching → keep everything updated
  • Phase 6 · Security tooling → the eyes and ears: logging, scanning, secrets
  • Phase 7 · Operations → access (RBAC (Role-Based Access Control)/PIM/MFA (Multi-Factor Authentication)), storage, CI/CD (Continuous Integration / Continuous Delivery), cost
  • Phase 10 · Resilience & Response → backup/DR + incident response — do this alongside the capstone
  • Phase 8 · Capstone → build it all from one repo, assess it, document it, then destroy & rebuild
  • Phase 9 · Market Add-ons → Kubernetes, AWS, certs — save for last, to broaden

A few validation steps borrow a resource from a later phase — e.g., the Azure Firewall test in 2.7 uses the Linux VM you build in Phase 4. That's expected; just loop back and validate once that VM exists.

Golden cost rule: run only the VMs the current phase needs, deallocate every night, and delete the pricey extras (Azure Bastion, Azure Firewall, Application Gateway, AKS (Azure Kubernetes Service)) the moment you finish validating them. Fully torn down, the lab costs about $0 — left running, it does not. The Phase 0 budget alert is your safety net.

Engineer's daily habits (rules of thumb worth memorizing)

Start of every session — confirm your footing before you build: az account show (right subscription?), terraform version, git status, then git pull --rebase. Two minutes here prevents most wrong-place / stale-login / merge-mess mistakes.

Terraform — always fmt → validate → plan, and read the plan like a receipt before apply. Never make manual portal changes to anything Terraform manages, or it will drift.

Git / GitHub — git pull --rebase before you push so history stays clean; commit small and often with clear messages; never commit secrets (if you do, rotate them — deleting the commit is not enough).

Security — default deny and open only what you can name; least privilege at the smallest scope; make admin rights temporary (PIM); secrets live in Key Vault, never in code.

Cost — deallocate VMs every night and delete the pricey extras (Bastion, Azure Firewall, AKS) the moment you finish validating. Idle resources still bill.

Troubleshooting — read logs first, guess second (systemctl status then journalctl -u); work the path in order (NSG → route → DNS → host). Narrate your steps — it is exactly how to think out loud in an interview.
